1. Introducción

Breve descripción del proyecto

El presente proyecto de final de ciclo consiste en el diseño, desarrollo a nivel de código y posterior despliegue en producción de "NBA Live". Se trata de una plataforma web integral e interactiva enfocada en la liga de baloncesto estadounidense (NBA). La aplicación proporciona a los usuarios información en tiempo real sobre marcadores de partidos, tablas de clasificaciones de las Conferencias Este y Oeste, estadísticas detalladas de franquicias y jugadores, y noticias relevantes del entorno deportivo.

Además de actuar como un panel informativo, "NBA Live" incorpora un componente interactivo diseñado para potenciar la retención del usuario. Esto se logra mediante la inclusión de un ecosistema de minijuegos lógicos y una sección de comunidad donde los usuarios registrados pueden interactuar, publicar reseñas y gestionar un perfil propio guardando sus equipos y jugadores favoritos en la nube.

Desde el punto de vista del Diseño de Interfaces (UX/UI), la plataforma ha sido concebida bajo una estética moderna, implementando tipografías de fácil legibilidad y una paleta de colores cuidadosamente seleccionada para transmitir dinamismo y profesionalidad, emulando la calidad gráfica de las aplicaciones deportivas líderes en el mercado actual y priorizando siempre la experiencia de navegación del usuario.

Desde el punto de vista técnico, el proyecto engloba la administración completa de la infraestructura subyacente. Esto incluye la contenedorización de los servicios mediante Docker, la programación de un servidor backend utilizando Node.js y Express, y la integración de una base de datos relacional PostgreSQL alojada remotamente (Supabase) para asegurar el almacenamiento persistente y seguro de la información.

Justificación

La elección de este proyecto surge de una motivación personal por combinar dos áreas de gran interés: el deporte y el desarrollo web avanzado. Sin embargo, la justificación académica radica en la necesidad imperante de demostrar un dominio integral (perfil Full-Stack) de las competencias técnicas exigidas hoy en día en el mercado laboral.

A lo largo del ciclo superior de Desarrollo de Aplicaciones Web (DAW), se han asimilado conceptos sobre programación en el cliente y servidor, el diseño lógico de bases de datos, y las metodologías modernas de despliegue continuo. Este Proyecto Final de Ciclo sirve para unificar esos conocimientos teóricos en un producto real. Al desarrollar y desplegar esta aplicación desde cero, se abarcan retos como la creación de APIs RESTful, el consumo eficiente de APIs de terceros, la administración asíncrona de sesiones descentralizadas mediante JWT, y el modelado riguroso de bases de datos relacionales.

Áreas de trabajo e implicación de los módulos

Para la consecución de los objetivos generales de este proyecto, se ha trabajado en diversas áreas que se corresponden de forma directa con los módulos cursados durante el ciclo de DAW:

Desarrollo Web en Entorno Cliente (Frontend): Crucial para la interfaz gráfica y la interactividad. Se ha empleado HTML5 para dar semántica a la estructura, CSS3 (mediante Flexbox y CSS Grid) para un diseño responsivo, y JavaScript puro (Vanilla JS). Mediante JavaScript se manipula dinámicamente el DOM, se gestionan eventos asíncronos y se realizan peticiones HTTP (mediante Fetch) para hidratar las vistas con datos del backend.

Desarrollo Web en Entorno Servidor (Backend): Utilizando Node.js y el micro-framework Express, se levantó un servidor encargado de enrutar las peticiones, consumir recursos de terceros y gestionar la lógica de negocio. Se han aplicado medidas de seguridad como el manejo de políticas de mismo origen (CORS) y la implementación de un sistema criptográfico mediante JSON Web Tokens (JWT).

Bases de Datos y Diseño Conceptual: El almacenamiento estructurado se ha delegado a PostgreSQL, operando bajo la plataforma Supabase. Se crearon tablas interconectadas para registrar usuarios, validar inicios de sesión (usando el algoritmo de hash Bcrypt), persistir el histórico de puntuaciones de juegos y salvaguardar las claves foráneas (Foreign Keys) que relacionan a los usuarios con sus favoritos.

Despliegue de Aplicaciones Web: Para el paso a producción, se recurrió a la contenedorización mediante Docker y Docker Compose. Esto permitió estandarizar los entornos de ejecución, asegurando que el código funcione sin problemas de compatibilidad en un servidor remoto.

2. Desarrollo del proyecto

El desarrollo ingenieril de "NBA Live" se ha abordado bajo un paradigma Full-Stack estricto. La división del sistema global en una arquitectura cliente-servidor separada promueve el desacoplamiento tecnológico, lo que favorece el mantenimiento del código a largo plazo y la escalabilidad del software.

2.1. Arquitectura y Stack Tecnológico

Para construir la plataforma, se ha seleccionado un ecosistema moderno que equilibra rendimiento y facilidad de mantenimiento modular:

  • Capa de Presentación (Frontend): Se optó por utilizar Vanilla JavaScript en lugar de depender de frameworks reactivos pesados. El diseño es Mobile-First, y la lógica se encuentra segregada en múltiples módulos independientes como auth.js, clasificacion.js, y minijuegos.js.
  • Capa Lógica (Backend): Se diseñó una API RESTful con Node.js y Express. Este servidor procesa las cargas de datos (payloads) de los formularios, interactúa con la base de datos PostgreSQL, y se comunica con las APIs estadísticas de terceros (BallDontLie, ESPN), protegiendo las credenciales.
  • Capa de Persistencia (Base de Datos): El almacenamiento a largo plazo recae en un motor PostgreSQL a través de Supabase DBaaS (Database as a Service).
  • Orquestación y Despliegue (DevOps): Mediante el archivo docker-compose.yml, se orquestan dos contenedores clave. En lugar de servir los archivos HTML directamente desde Node, se utiliza una imagen de nginx:alpine. Nginx actúa como un servidor proxy estático de alto rendimiento, gestionando el enrutamiento de los archivos visuales hacia el cliente, liberando al contenedor de Node para que se dedique exclusivamente a procesar las peticiones de datos de la API.

2.2. Diseño de la Base de Datos

Para dotar a la plataforma de funcionalidad persistente, fue imperativo desarrollar un modelo relacional eficiente estructurado en las siguientes tablas principales:

  • Tabla 'users': Almacena los registros de los usuarios. Contiene identificadores únicos generados secuencialmente, el nombre de usuario, el correo electrónico y la contraseña obligatoriamente hasheada. Incluye un campo entero denominado monedas para la gamificación.
  • Tabla 'favoritos': Actúa como tabla relacional para implementar el almacenamiento de preferencias. Contiene una clave foránea apuntando al ID del usuario y campos para almacenar el identificador del equipo o jugador externo.
  • Tabla 'reviews': Persiste la comunidad de la web. Registra reseñas asociando el ID del autor, una calificación entera (del 1 al 5), un texto y una marca de tiempo automática.

2.3. Definición de la API REST (Rutas del Servidor)

El backend Node.js expone un contrato de interfaces para que el frontend pueda operar con los datos. Las rutas principales son:

  • POST /api/register: Recibe datos de un nuevo usuario, encripta la contraseña e inserta la fila en la tabla. Devuelve un Token JWT.
  • POST /api/login: Valida las credenciales contra la base de datos. Si el hash coincide, emite un nuevo Token de autorización.
  • GET /api/games: Endpoint Proxy. El servidor consulta su caché y, si no tiene los datos recientes, consulta a la API de la NBA externa y devuelve el JSON.
  • POST /api/favorites: Ruta protegida (requiere JWT). Inserta una nueva fila asociando el usuario autenticado con la entidad deportiva.
  • PUT /api/coins: Ruta protegida. Suma la recompensa de los minijuegos al perfil del jugador en PostgreSQL.

2.4. Módulos Especialmente Relevantes

Sistema Inteligente de Caché para Consumo de APIs Externas

La plataforma muestra datos interactuando con interfaces gratuitas externas que imponen estrictos límites de uso (Rate Limits). Si la aplicación web solicitaba datos constantemente, la dirección IP del servidor quedaba bloqueada por saturación.

Para solucionar este problema, se desarrolló un sistema de caché en la memoria RAM del propio proceso de Node.js. Si los datos solicitados han sido requeridos recientemente y aún no han caducado según un TTL (Time To Live), el servidor devuelve la respuesta clonada desde su memoria. Solo si la caché expiró, el servidor contacta con la API de la NBA, centralizando el tráfico externo y salvando la plataforma de caídas.

Modularización del Código Frontend (Vanilla JS)

Al no contar con un framework que estructure el proyecto por defecto, se hizo uso intensivo del estándar de módulos de ECMAScript (ES6 Modules). Todo el código JavaScript de la capa de presentación fue estrictamente segmentado por responsabilidades. Por ejemplo, las funciones encargadas de realizar peticiones HTTP mediante fetch se aislaron en un archivo dedicado, separándolas de las funciones responsables de la inyección visual en el DOM. Esta arquitectura de separación de responsabilidades (Separation of Concerns) evita la proliferación de código desorganizado y simplifica drásticamente el proceso de depuración (debugging) directo en la consola de herramientas del navegador.

Carga y Gestión de Variables de Entorno Seguras

Para asegurar la infraestructura backend desde el primer minuto de ejecución, se integró el módulo nativo dotenv en el núcleo del servidor Node.js. Esto permite que la API analice de forma transparente archivos ocultos del sistema y cargue en la memoria volátil las credenciales maestras de la base de datos (Supabase) y la semilla criptográfica (JWT Secret). Esta técnica programática garantiza que ningún dato o contraseña sensible termine publicado por error y expuesto públicamente en los repositorios de control de código de GitHub.

2.5. Análisis Técnico de Código (Implementaciones Clave)

A continuación, se transcriben bloques de código fundamentales que cimentan el correcto desempeño de "NBA Live".

A. Mecanismo de Caché en Memoria (Node.js)

// ============ CACHÉ EN MEMORIA (server.js) ============
// Objeto que retiene la información en la memoria RAM
const cache = {
    games: null,
    gamesTimestamp: 0
};

// 30 segundos de vida útil
const CACHE_DURATION = 30000; 

app.get('/api/games', async (req, res) => {
    try {
        const now = Date.now();
        // Verificamos existencia y validez
        if (cache.games && (now - cache.gamesTimestamp) < CACHE_DURATION) {
            return res.json(cache.games);
        }
        
        // Petición asíncrona al proveedor externo
        const response = await fetch(`https://api.balldontlie.io/v1/games`);
        const data = await response.json();
        
        // Almacenamos el resultado fresco
        cache.games = data;
        cache.gamesTimestamp = now;
        
        res.json(data);
    } catch (error) {
        res.status(500).json({ error: 'Error de red' });
    }
});

B. Middleware de Verificación de Identidad JWT (Node.js)

// ============ MIDDLEWARE: Verificar JWT ============
function authenticateToken(req, res, next) {
    const authHeader = req.headers['authorization'];
    const token = authHeader && authHeader.split(' ')[1]; 

    if (!token) {
        return res.status(401).json({ error: 'Denegado. Se requiere token.' });
    }

    try {
        const user = jwt.verify(token, process.env.JWT_SECRET);
        req.user = user; 
        next(); 
    } catch (error) {
        return res.status(403).json({ error: 'Token inválido o expirado.' });
    }
}

D. Encriptado de Contraseñas (Node.js)

// ============ HASHING CON BCRYPT ============
const bcrypt = require('bcrypt');
const SALT_ROUNDS = 10;

app.post('/api/register', async (req, res) => {
    const { username, email, password } = req.body;
    try {
        const hashedPassword = await bcrypt.hash(password, SALT_ROUNDS);
        await db.query(
            'INSERT INTO users (username, email, password_hash) VALUES ($1, $2, $3)',
            [username, email, hashedPassword]
        );
        res.status(201).json({ message: 'Cuenta creada seguro.' });
    } catch (error) {
        res.status(400).json({ error: 'El registro falló.' });
    }
});

E. Prevención de Inyección SQL en Inserciones (Node.js)

Este bloque demuestra el estándar de seguridad adoptado para las entradas de texto libres por parte de los usuarios, salvaguardando la integridad de la base de datos contra intenciones maliciosas o caracteres de escape no filtrados.

// ============ INSERCIÓN DE RESEÑAS ============
app.post('/api/reviews', authenticateToken, async (req, res) => {
    const { rating, comment } = req.body;
    
    // Validación de integridad (Sanitization)
    if (!rating || rating < 1 || rating > 5) {
        return res.status(400).json({ error: 'Valoración incorrecta.' });
    }

    try {
        // Uso obligatorio de Consultas Parametrizadas ($1, $2, $3)
        // Esto neutraliza por completo los ataques de SQL Injection
        await db.query(
            'INSERT INTO reviews (user_id, rating, comment) VALUES ($1, $2, $3)',
            [req.user.id, rating, comment]
        );
        res.status(201).json({ message: 'Reseña insertada exitosamente.' });
    } catch (error) {
        res.status(500).json({ error: 'Fallo al procesar la inserción.' });
    }
});

3. Dificultades encontradas y posibles soluciones

El desarrollo ha planteado diversos obstáculos técnicos de consideración:

3.1. Restricciones CORS y Gestión de Rate Limits

Dificultad: En el prototipo inicial, el navegador hacía llamadas directas a los servidores estadísticos de la NBA. Los navegadores imponían bloqueos de CORS (Cross-Origin Resource Sharing). Además, las APIs gratuitas imponían límites de cuota de uso, bloqueando nuestra aplicación.

Solución: Se configuró el Backend de Node.js como un servidor Proxy. Puesto que las restricciones CORS aplican exclusivamente al navegador y no a las comunicaciones entre servidores, los problemas se desvanecieron. Esto justificó la creación del módulo interno de Caché analizado anteriormente, salvando los límites de cuota.

3.2. Estructuración del Frontend sin Frameworks

Dificultad: Mantener y actualizar elementos visuales simultáneamente (como marcadores en vivo y puntuaciones) utilizando JavaScript nativo causaba un código muy acoplado y difícil de mantener.

Solución: Se optó por refactorizar el código aplicando ES6 Modules (import/export), creando ficheros funcionales independientes. Se justificó la implementación de promesas asíncronas (async/await), lo cual aplanó el código y mejoró la legibilidad lógica.

3.3. Persistencia Segura del Estado (Stateless)

Dificultad: Al navegar físicamente por varios archivos .html, el usuario se deslogueaba entre las redirecciones de la web.

Solución: Se recurrió al estándar JWT almacenado de forma latente en el localStorage del dispositivo del cliente. La web invoca silenciosamente a un script hidratador que interpreta el token y modifica la barra de menú instantáneamente sin cargar el servidor.

3.4. Gestión de Variables de Entorno y Seguridad en Contenedores

Dificultad: Durante el proceso de contenedorización con Docker, surgió el problema de cómo inyectar las cadenas de conexión a la base de datos de Supabase y la firma JWT secreta sin tener que escribir (hardcodear) estos valores sensibles dentro del código de la imagen Dockerfile, lo que representaría una vulnerabilidad crítica.

Solución: Se implementó un archivo .env local que se sincroniza exclusivamente mediante directivas internas de docker-compose.yml. El contenedor lee estas variables durante el tiempo de ejecución en lugar de almacenarlas durante la construcción, manteniendo la imagen de Node.js agnóstica y completamente segura frente a posibles filtraciones de código.

4. Posibles mejoras

A la luz de los conocimientos adquiridos, existen múltiples áreas de mejora profunda para las versiones futuras:

Integración de un Framework Reactivo y TypeScript

Transicionar la capa de presentation hacia un framework declarativo (como React.js o Vue.js) reduciría significativamente la complejidad al delegar los re-renderizados del DOM al motor interno de la librería. Adicionalmente, reescribir todo el código implementando TypeScript agregaría tipado estático, eliminando un altísimo porcentaje de errores en tiempo de ejecución.

Arquitectura Event-Driven: WebSockets

La web confía actualmente en peticiones cronometradas (HTTP Polling). Implementar el protocolo WebSockets permitiría establecer un túnel de datos persistente. El servidor backend podría empujar de forma reactiva las modificaciones de los marcadores deportivos, proporcionando un entorno genuino de "Tiempo Real" a los espectadores.

Refuerzo de Ciberseguridad (Cookies HttpOnly)

El almacenamiento del Token JWT en localStorage expone el sistema a posibles ataques XSS. La mejora obligada consistiría en transicionar dicho almacenamiento hacia Cookies inyectadas por el servidor, configuradas con las propiedades HttpOnly y Secure, blindando la arquitectura frente a secuestros de sesión informáticos.

5. Resultados

La finalización de este proyecto ha dado como fruto una plataforma web deportiva ("NBA Live") madura, de alta disponibilidad y plenamente funcional, cumpliendo con total rigurosidad los objetivos iniciales.

Desde el punto de vista del diseño y la experiencia de usuario, la correcta aplicación de directivas CSS Grid y Flexbox ha garantizado que la plataforma supere las métricas de usabilidad básicas. El diseño responsivo permite que el contenido dinámico fluya y se adapte sin problemas en resoluciones estrechas de dispositivos móviles sin romper el modelo de caja ni requerir descargas adicionales. A su vez, al prescindir de dependencias externas pesadas, el tiempo de primera carga de la web (Time to Interactive) es prácticamente instantáneo, un aspecto muy penalizado en proyectos similares construidos con tecnologías inadecuadas.

Se ha logrado materializar una solución orquestada Full-Stack. El microservicio backend sobre Node.js ha demostrado su fiabilidad extrema actuando como un escudo proxy. El vital sistema de caché ha sido el auténtico núcleo de valor que ha garantizado un flujo informativo veloz hacia el usuario, mitigando el riesgo de bloqueos por límite de peticiones (Rate Limiting).

La base de datos operada por Supabase se integró con total naturalidad, habilitando el despliegue seguro de cuentas de usuario privadas. Mediante el uso de procesos criptográficos (Bcrypt y JWT), se ha asegurado el almacenamiento de miles de perfiles que pueden registrar sus preferencias relativas a los equipos y formar parte de una comunidad web.

Como guinda tecnológica, se destaca la contenedorización total de la solución mediante Docker y Docker Compose, garantizando que esta plataforma sea un software portátil, preparado para la empresa y desplegable sin errores en servidores Linux modernos.

7.1. Manual Técnico (Instalación y Configuración)

La plataforma puede ser ejecutada de manera local o a través de despliegue contenerizado estandarizado orientado a producción.

A. Entorno Local (Con Visual Studio Code)

Requisitos:

  • Editor Visual Studio Code instalado.
  • Entorno asíncrono Node.js y npm instalados.
  • Extensión "Live Server" integrada en VS Code.

Pasos para arranque local:

  1. Abrir VS Code y seleccionar Archivo > Abrir Carpeta... eligiendo el directorio raíz nba/.
  2. Llamar a una terminal anclada (Terminal > Nueva Terminal).
  3. Navegar al backend con: cd nba-server
  4. Instalar dependencias necesarias (Express, PostgreSQL, JWT, Bcrypt) ejecutando: npm install.
  5. Crear un archivo .env en la subcarpeta nba-server albergando las variables:
    DATABASE_URL=postgres://tu_usuario:tu_contraseña_privada@dominio.supabase.co:5432/postgres
    JWT_SECRET=escribe_tu_llave_secreta_aqui
  6. Iniciar el bucle de peticiones con el comando: node server.js.
  7. Hacer clic derecho sobre el archivo nba.html en VS Code y lanzar la opción "Open with Live Server" para hidratar visualmente la plataforma en el navegador.

B. Despliegue Automatizado Mediante Docker

Para entornos productivos o tribunales de evaluación, el proyecto presenta su faceta DevOps contenerizada definitiva.

Requisitos:

  • Daemon Docker Engine y Docker Compose instalados.
  • Puertos TCP 8080 y 3000 libres en la máquina anfitriona.

Pasos para despliegue automatizado:

  1. Garantizar que el archivo .env esté debidamente posicionado en nba-server/.
  2. Abrir una terminal en la raíz del proyecto y teclear el orquestador: docker-compose up -d --build
  3. Docker instanciará una imagen de servidor web ultra-ligero nginx:alpine y compilará la imagen Node.js del backend. Ambos servicios quedarán operando unificados.
  4. Acceder desde el navegador a la ruta local: http://localhost:8080.

Nota sobre Virtualización: La concepción puntera del presente proyecto web descarta el uso de Máquinas Virtuales pesadas y obsoletas (VMDK/OVA). El empaquetado aislado de dependencias se ha acometido recurriendo al empleo de Contenedores Ligeros (Docker), el estándar incuestionable del mercado laboral (filosofía DevOps) para despliegues ágiles.

7.2. Manual de Usuario Final

La aplicación "NBA Live" dispone de una navegabilidad altamente funcional, asegurando un aprendizaje orgánico inmediato.

Para Usuarios Visitantes (No Registrados):

Para Usuarios Registrados:

  • Gestión de Alta (Login/Signup): Al formalizar su correo y contraseña en signup.html, el sistema genera su cuenta. La barra superior reacciona asíncronamente reflejando su Alias de usuario junto con su saldo base inicial de "Monedas" lúdicas.
  • Panel de Favoritos: El usuario visualizará botones con forma de "estrella" al consultar información de jugadores o equipos. Pulsarlos genera una petición que archiva el elemento en su directorio privado, permitiendo un acceso recurrente veloz en su pestaña de "Favoritos".
  • Escritura en Comunidad: Quedan facultados de emitir inputs evaluativos textuales y numéricos (estrellas) en el tablón público de reseñas, sumando al debate general de la plataforma de forma visible para todos los visitantes.
  • Minijuegos Lúdicos: En el área de juegos, el usuario encontrará diversas mecánicas, como la "Trivia" visual de estadísticas históricas o el clásico "Ahorcado" sobre nombres de jugadores de la liga. Estas mecánicas no solo amenizan la estancia en la web, sino que recompensan económicamente de forma virtual sus victorias lógicas. El servidor backend de Node.js se encarga de guardar estos progresos en cada sesión para que nunca se pierda el avance acumulado.
  • Desvinculación (Cierre de Sesión): Pulsar el botón de cierre elimina definitivamente el token latente jwt_token en la memoria del navegador, cerrando el terminal operativo y salvaguardando en local su identidad.

7.3. Entorno de Desarrollo y Herramientas

Para la correcta gestión del proyecto se han empleado herramientas estandarizadas complementarias al código fuente. El control de versiones se ha efectuado mediante repositorios de Git y GitHub, lo cual permitió mantener un histórico limpio de todas las fases del desarrollo y asegurar la persistencia en la nube ante posibles fallos locales. Esta práctica de control de ramas es vital de cara a la inserción en el mercado laboral. Por otro lado, la verificación y prueba funcional de los Endpoints de la API se llevó a cabo utilizando Postman, una plataforma que facilitó la inyección de Tokens JWT y la validación de respuestas JSON de manera previa a su integración definitiva con las pantallas del Frontend.
